2. CHALLENGE DE CHAQUE FAMILLE D/E

Références relatives à analysis/d6/real_execution_calibration_v1.
Les invariants restent en vigueur. Les alternatives ci-dessous ne sont PAS
déployées implicitement et aucune réussite de modèle n'est une preuve production.

P1 — production_evidence_source.py:24-32, d6112e1 : authenticité/contexte/freshness.
Risque : faux compte, cache, replay. Minimum : collecteur direct isolé du
supervisor, TLS/RPC validés, nonce/context et reçu signé ; firme tierce inutile.
Une clé sous le même SID ne protège PAS d'un supervisor malveillant de ce SID.
Sous ce modèle d'attaque, compte de service/ACL distinct ou hôte externe requis.

P2 — source:34-45 : cinq composants, counts/digests, origin wallet_creation,
filters={}, frontier commun. Risque : exposition/fees omis. Minimum exact :
inventaire exhaustif avec provenance du checkpoint, historique complet et clôture
de pagination ; recoupement RPC à bloc fixé et archive des ordres hors chaîne.
Une liste vide ne prouve pas l'absence globale. Hash commun = cohérence des octets,
pas preuve que les données viennent du même instant ou qu'un élément ne manque pas.

P3 — source:46-65 et adapters.py:72-105 : baseline, ancêtres, flags, projections,
absence d'activité étrangère. Risque : fork, compte mélangé, double comptage.
Minimum : baseline vérifié + journal monotone, conservation cash/shares et toutes
sources pertinentes. Les booléens de complétude ne peuvent créer l'information.

P4 — source:68-89 / adapters.py:37-70 : timeout5s, lock, fills/fees/terminal.
Risque : race, résultat submit non final, fees manquants. Minimum : un collecteur
sérialisé, identités de trades uniques, effets indépendants et terminal vérifié.
Pas besoin de faire un ordre pour prouver ce chemin avant armement.

P5 — production_provider.py:11-28, d6112e1 : hors Git,8MiB, noms, pas de links,
JSON strict ; publication atomique. Risque : fuite, ambiguïté JSON, fichiers
partiels/substitués, mémoire non bornée. Un spool local privé est suffisant.
8MiB ne doit pas être pris comme preuve qu'un wallet arbitrairement ancien tient
dans le format ; en cas de dépassement, bloquer, jamais tronquer l'inventaire.

A1 — production_authority.py:10-28, d6112e1 : clés/kinds/provider/context/policy,
signature. Risque : auto-approbation, mauvaise source, signature hors scope.
Minimum : clé d'un collecteur identifié et policy approuvée une fois hors du
supervisor. Pas besoin d'une clé par preuve ni d'une entreprise de certification.
Une clé générée automatiquement est un candidat, pas une décision de confiance.

A2 — authority:30-36 : baseline72h, autres5s. Risque : données périmées.
Pour cash/book/clock, garder une fraîcheur runtime bornée. Pour tests/audit/code,
une attestation durable liée à codehash+policy+déploiement, avec révocation et
vérification actuelle de ces liens, peut couvrir l'invariant sans resign toutes
les5s. Le modèle teste l'invalidation sur changement ; pas encore preuve complète
de révocation ou d'équivalence à déployer. Le guard actuel reste inchangé.

Un seul journal indépendant et relisible suffit ; une seconde base n'est pas

3. LE MINIMUM LÉGITIME POUR WALLET-WIDE

Pas de tiers magique nécessaire. Un collecteur direct indépendant peut consommer
CLOB/Data API/WS utilisateur et RPC d'archive, conserver les originaux et publier
les mêmes enveloppes actuelles. La décision de confiance porte sur le principal,
le programme vérifié, les sources et les droits, pas sur le mot 'provider'.

Cash : balanceOf du collateral exact à bloc fixé + balance CLOB, disponibilité
et réservations ; positions : token universe découvert dans tous transferts /
mint/burn/split/merge/redeem depuis origine puis balances par token, Data API en
contre-vérification ; ordres : scope exchange de tous les makers/credentials,
pagination live, archive d'IDs terminaux ; fills : trades attribués au wallet,
receipt/logs de settlement finalisés ; fees : effets cash/shares de chaque fill,
pas simple taux. Compter toutes corrections et prouver la conservation des flux.

LIMITATION INFORMATIONNELLE DÉMONTRÉE : un ordre annulé sans fill, dont l'ID est
perdu, ne change ni la liste live ni les fills on-chain. Deux historiques distincts
produisent ces mêmes observations. Un nouveau signataire ne peut pas reconstituer
cette information. Le test de contre-exemple est explicite dans le modèle.
L'invariant littéral actuel 'tous terminaux depuis création' exige une archive
complète/exchange export ou une autre source historique. Les GET examinés ne la
promettent pas. On ne déclare donc pas wallet_creation=true après pagination vide.

Un checkpoint actuel prouvé + aucun ordre/engagement inconnu + journal complet
depuis T0 pourrait préserver l'invariant économique 'aucune exposition inconnue'.
Mais il ne préserve PAS l'invariant littéral d'historique exhaustif. Ce serait un
changement explicite de contrat, pas une simplification équivalente démontrée.
Il n'a pas été appliqué. Si l'historique exigé n'existe nulle part, il faut décider
ce contrat après revue, pas fabriquer un provider qui le signerait.
