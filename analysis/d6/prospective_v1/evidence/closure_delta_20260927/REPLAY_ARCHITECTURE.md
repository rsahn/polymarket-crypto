# Replay recovery candidate: exact histories on disk

`disk_replay.py` is offline and unadopted. It reuses `ProspectiveEventAdapter._apply`, `Ledger` and `BookTape` without changing any economic formula or rule. `observe` is explicitly disabled. It does not implement checkpoints or production recovery. Restart means reading the immutable source again into **new** scratch databases. Existing scratch files are never reopened/overwritten, including after failure.

Two databases hold journal IDs and economic state. All historical trade states, ledger IDs/events, fee annotations, causal book histories, depth (including tombstones), positions, reservations and accounting rows are exact disk containers. Ordered iteration and numeric key equality are preserved. One-level dictionary writes are persisted for the specific mutations used by the unchanged transition. No time-based pruning, latest-book shortcut, duplicate-cache eviction, fee fallback or depth reset is introduced. Values use tagged JSON preserving Decimal/tuple/key types; no executable deserialization.

RAM retains cash/initial/realized/fees/turnover/last timestamp, last marks, partition identity, journal sequence/hash, ended flag, current record and current dictionary values. The existing `Ledger.mark` materializes active positions, and `BookTape.observe` constructs one token's depth. Accordingly working memory still depends on largest record/key/depth, active positions/marks, and SQLite native allocations. None has a frozen protocol-wide byte bound. Each SQLite connection requests a 2 MiB page cache and file temp storage; that is not an RSS guarantee. Slices/materialize are deliberately O(N) diagnostic interfaces and are not used in recovery/stress. The full-history evaluator is not switched to this candidate.

Memory growth from the Python history lists/maps has been externalized. There is **no unconditional bounded-RSS or 168h claim**. MARK stress peak rises from 32,481,280 to 34,668,544 bytes between 10k and 100k events; the separate book-history case in the same process remains at 34,672,640 bytes across 10k–60k events. These are cumulative peak working sets, not independent per-case baselines or proof of an asymptotic bound. Exact attribution of the small native-process rise is unproven.

Throughput is not universally constant: fee annotations can scan old fills, historical as-of book lookups can scan backwards, settlement scans prior trade states, and marks inspect positions. These preserve semantics but may increase recovery time. Finite size, active-cardinality and execution-time bounds are absent. Thus **REPLAY_CAPACITY_UNQUALIFIED** remains while the specific in-memory history blocker is materially reduced.

Equivalence: canonical snapshots include cash/reservations/positions/cost/fees/realized/equity, fills, accounting, trade stages/quantities, all books, remaining depth, fee annotations and ended status. Tests compare seven prefixes (empty through settled/session-end), replay from source again, two tokens/rotation, delayed fee annotations and same-content distinct books. Final sequence/hash/identity match; invalid fee/depth/duplicate/torn cases reject. No production strategy or sealed dataset is invoked.

Stress sizes were fixed before measurement: 100,000 MARKs; 60,000 SIGNAL/ENTRY_INTENT/ENTRY_BOOK events (20,000 trade states/books, no fills). The latter is a schema/engine scalability workload, not the frozen strategy's cadence or economics. Both streams validate the original journal chain and retain cash500. Source SHA remains unchanged. Recovery times exclude generation and source hashing. Failed preliminary tooling attempts are preserved separately. Disk scratch is output work storage, not a qualified checkpoint.
