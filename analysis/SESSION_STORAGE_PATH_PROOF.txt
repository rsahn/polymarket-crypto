2. Historical implementation reconstruction

The wallet runtime is the native ERC1967 beacon-proxy template, not a UUPS wallet.
The proxy uses STATICCALL implementation() on the beacon from its fixed ERC1967
beacon storage slot, then DELEGATECALL to that returned implementation. Its own
runtime contains no storage setter. Factory/id immutable args match the known
factory and owner-based wallet id.

At creation and the terminal block, the beacon slot contains the stated beacon,
the UUPS implementation slot is zero, and pinnedImplementation(wallet) is zero.
Crucially, implementation() was also called with from=wallet: the beacon dispatches
by msg.sender, so a call without that context alone would not establish this.

ALL beacon logs were queried in 115 contiguous ranges over the requested interval:
zero logs, including zero Upgraded, OptedIn and OptedOut events. Source review of
DepositWalletBeacon.sol proves that _setImplementation (line 115) always performs
SSTORE followed by LOG2 Upgraded; upgradeTo (161) is its only post-constructor
entry. It also probes the wallet interface; failure reverts both mutation and log.
The pin mapping is Solidity slot 0. optOut (222) and optIn (229) always emit their
respective events after assigning/deleting that mapping. No external delegatecall,
arbitrary slot write, proxy upgrade or selfdestruct exists in beacon runtime.
Thus, under canonical log completeness, the same implementation was used over the
entire interval, including intermediate blocks; this is not inferred just from
equal endpoint values. No forwarder/legacy implementation was active for this wallet.

4. Other paths and storage separation

execute (271) requires the factory caller and a valid owner/session signature;
it checks wallet identity, nonce and deadline. Each batch operation uses CALL,
not DELEGATECALL. A session signer cannot target the wallet or beacon. An owner's
self-call can reach the setters above, but cannot bypass their required emit.
Relayer/factory access is not an arbitrary wallet-storage writer. Reentrancy via
an external target does not acquire onlySelf; an independently valid nested batch
still traverses the same emitting setters.

The complete inherited AST SSTORE inventory is archived in session_storage_path_proof.json.
Other writes are nonce, pause timestamp, owner/pending-owner/deadline/handover-nonce,
and Initializable's fixed slot
0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffbf601132.
They do not address either authorization mapping. Ordinary Solidity storage layout
is empty; there are no unaccounted Solidity state assignments in DepositWallet.
Receiver fallback only handles token receipt selectors or rejects; ERC1271/EIP712
signature paths are view/pure. There is no dynamic library link or arbitrary
delegatecall/selfdestruct in the active implementation or inherited execution paths.
Ownership changes modify ownership state, not signer mappings. initialize (147)
sets the owner only and is guarded by initializer. Factory upgrades cannot directly
rewrite this wallet's storage or beacon pointer. Native wallet optIn/optOut calls
only change the emitting beacon pin mapping, not authorization storage.

The proof assumes standard EVM/compiler semantics and keccak collision/preimage
resistance, as do address/signature/storage proofs generally. This is a manual
source argument bound to an exact locally rebuilt runtime, with targeted AST and
adversarial evidence checks; it is not advertised as a machine-checked theorem
for arbitrary future implementations.

5. Zero-signers conclusion

The creation boundary, canonical receipt and native proxy code establish initial
zero authorization mappings. Additionally, genesis_call_trace.json records the
actual CREATE2 constructor and returned runtime. Its exact 35-byte constructor
CODECOPYs the proxy, SSTOREs only the ERC1967 beacon slot, then RETURNs. This
rules out an unexamined constructor pre-populating signer mappings while returning
the expected runtime. The trace is a read-only debug_traceTransaction result, not
a transaction. An adversarial initcode mutation is rejected by the verifier.
All successful subsequent mapping mutations must
emit one of the SIX signer events. The complete wallet log archive contains only:
OwnershipTransferred=1, Initialized=1, Execution=21, BatchExecuted=2.
The 21 executions decode to ERC20 approve / ERC1155 setApprovalForAll only; no
authorization call is concealed in those recorded batches.

Therefore, for this wallet and the stated interval, no secp256k1 or P-256 session
signer was authorized on-chain. HISTORICAL_ZERO_SIGNERS_PROVEN=true is justified
within this scope. Natural expiry of a historically authorized session signer is
not a remaining blocker for this interval and wallet. No assertion is made that
expiration cancels orders generally, or that other wallets have this property.
